# ADR-0004: 发现层采用 EndpointRecord 记录模型

- **状态**：Accepted
- **日期**：2026-11-24
- **决策者**：架构 owner、协议 owner
- **关联代码**：`src/core/registry.h`、`src/backends/nng/registry.cc`、`src/backends/memory/registry.cc`
- **取代**：—

## 背景

旧的发现表以 `kind + name` 为键存**单值**，并用空串引用计数表示「有几个订阅者」。这带来三个实际缺陷：

1. 两个同通道 Reader 共用一条记录，删掉一个就把整条订阅关系删了，另一个收不到消息。
2. 没有身份概念，注销只能按 `kind+name`，无法表达「注销我注册的那一个」。
3. 记录里没有后端标识，跨后端部署时无法过滤不兼容的地址。

## 决策

**决定改为记录模型：`EndpointRecord{id, kind, name, backend, address}`，注册返回不透明 `id`，注销只按 `id`，查询返回全部匹配记录。**

边界：

1. 同一 `kind+name` 允许多条记录，`Query` 必须全部返回，不得互相覆盖。
2. Reader 即使没有监听地址也独立登记（`address` 为空串），删一个不影响同通道其他 Reader。
3. `Watch` 在注册回调的同一串行化域内取得一致初始快照（按 `id` 排序，含注册前已存在的记录），此后每次增删派发**完整当前快照**；回调内禁止调用 `IRegistry`。
4. `Clear()` 幂等：清空记录与订阅，之后迟到的 `Unregister(id)` 为 no-op，再次 `Register`/`Watch` 可重启且看不到旧记录。
5. 线协议只做**追加式**变更：`REG`/`UNREG` 在行尾追加可选 `id`/`backend`，旧版忽略；新版对缺失字段按 `kind+name+address` 派生稳定兼容 id；`QLIST` 不可用时回退 `LIST`。

## 后果

- **正面**：同通道多 Reader 隔离；注销语义明确；`backend` 过滤具备数据基础。
- **正面**：删除不再依赖引用计数，`Clear` 后可干净重启。
- **负面 / 成本**：`id` 要跨进程传递，协议向后兼容需要派生规则与回退路径（`QLIST`→`LIST`），实现与测试都变复杂。
- **负面 / 成本**：Watch 派发完整快照，订阅者数量增大时单次派发体积上升。
- **如何验证仍被遵守**：`batch3_contract_test`（多记录/backend 过滤、Watch 快照、Clear 重入、注册失败无残留、Reader 删一个不影响另一个）；`cross_*` 四组验证新旧协议互通。

## 备选方案

| 方案 | 未采纳原因 |
| --- | --- |
| 保留单值表 + 引用计数 | 无法表达「注销我这一条」，且计数与实际连接状态易脱节 |
| 用 `address` 作为隐式身份 | Reader 没有地址，且地址可能变化；不能作主键 |
| 引入外部服务注册中心（etcd/consul） | 引入进程外依赖，与「同机零配置」定位冲突 |
