# ADR-0007: 文档分层与过程记录出库

- **状态**：Accepted
- **日期**：2026-11-24
- **决策者**：文档 owner、架构 owner
- **关联代码**：`docs/`、`Doxyfile`、`.github/workflows/docs.yml`
- **取代**：—

## 背景

整理前 `docs/` 只有一层，9 篇文档共约 1370 行，其中过程类内容超过一半：验收快照、原始规划稿、落地差异记录、逐批提交清单。三类内容混在一起：

- 「现在是什么」——契约与架构，改代码前必须看；
- 「当时为什么」——决策理由，只在判断能否改动时需要；
- 「当时做到哪」——过程流水，一年后没有任何判断价值。

后果是可观察的：`kAccepted` 的送达语义同时写在 `writer.h` 注释、`architecture.md` 与发布说明三处，措辞已不一致；`implementation.md` 里的 GitHub 行号链接因目录搬迁全部失效；读者无法判断一篇文档是否仍然可信。

## 决策

**决定按内容性质把文档分成三层，过程记录整体移出仓库，公共接口文档改为源码注释生成。**

边界：

1. `docs/architecture/`（现在是什么）、`docs/decisions/`（当时为什么）、`docs/guides/`（怎么做）三层，各层有明确的「不存放」清单。
2. 过程记录（阶段计划、验收快照、逐批提交清单、落地差异、过期设计稿）**移出仓库**，归档到团队 Wiki；仓库内**不设** `docs/history/`。git 历史是过程事实的权威来源。
3. 「一事一处」：一个事实只在一篇文档写全，其它位置只允许一句话摘要 + 链接。
4. 公共接口的 API 文档以 `include/firefly/**` 的 Doxygen 注释为唯一事实源，生成物 `docs/api/` 不纳入版本控制。
5. 行为契约的每条断言必须能对应到测试；无法验证的内容不属于 `contracts.md`。
6. `docs/` 不接受提交号、批次号、Issue/PR 号、审查人姓名与临时版本标记。

## 后果

- **正面**：过程类内容归零，每篇文档都能被单独判断是否可信。总量反而上升（新增 7 篇 ADR 与规范本身），这是把口头知识显式化的代价，不是膨胀——判据是每篇都有明确触发条件，见 5.1。
- **正面**：公共 API 文档随代码走，签名改动在同一个 PR 内完成，不再有「文档落后于代码」的窗口。
- **正面**：ADR 保留决策轨迹，删掉过程文档不再丢信息。
- **负面 / 成本**：迁移需要一次性投入（拆分 3 篇混合文档、写 7 篇 ADR、改造 5 个公共头注释），约 4–5 人日。
- **负面 / 成本**：过程文档离开仓库后，查历史要跨系统（git + Wiki）；靠 tag 注释记录归档地址缓解。
- **负面 / 成本**：CI 增加 Doxygen、链接、孤儿文档、索引一致性四项门禁，首次接入必然暴露存量问题。
- **如何验证仍被遵守**：`docs.yml` 的四项检查 + `README.md` 行数检查 + PR 模板的文档勾选项；每季度人工审计一次（`documentation.md` 6.4）。

## 备选方案

| 方案 | 未采纳原因 |
| --- | --- |
| 保留现有结构，只补充索引 | 混合文档不拆分，读者仍无法判断可信度；过程内容会持续增长 |
| 在仓库内保留 `docs/history/` 只读归档 | 只读约束无法自动执行，实测会重新长成活跃文档；且与「过程不进仓库」的判据冲突 |
| 用 Wiki 完全替代仓库文档 | 文档与代码不在同一提交中，无法做到「同一 PR 更新」，评审也看不到差异 |
| 手写 API 文档 | 签名一变就过期，且与源码注释形成双份事实 |
