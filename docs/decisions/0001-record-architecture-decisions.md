# ADR-0001: 用 ADR 记录架构决策

- **状态**：Accepted
- **日期**：2026-11-24
- **决策者**：架构 owner、文档 owner
- **关联代码**：`docs/decisions/`、`docs/guides/documentation.md`
- **取代**：—

## 背景

重构周期内，决策的理由散落在规划稿、发布说明与提交信息里。规划稿被实现取代后要么删掉（理由随之丢失），要么留在仓库里变成过时设计稿（读者无法判断是否仍然有效）。两种结果都让「当年为什么这样定」不可追溯：新成员看到的是结论，看不到代价与被否方案。

同时，同一事实在代码注释、`architecture.md` 与发布说明里各写一遍，措辞已经出现分歧。

## 决策

**决定用 ADR（Architecture Decision Record）承载一次性决策的理由与代价，现状描述与操作步骤不进 ADR。**

边界：

1. 一决策一文件，编号 `NNNN` 单调递增、永不复用、永不重排；文件一旦 Accepted 只能改状态与勘误，不得改写结论。
2. 决策被推翻时新增一条 ADR，并在旧文件顶部标注「已被 ADR-XXXX 取代」；旧文件保留。
3. ADR 只解释「为什么」，不描述「现在是什么」——现状一律指向 `docs/architecture/*`。
4. 不做的事也要写（No-go ADR），避免同一提议被反复讨论。
5. 索引 `docs/decisions/README.md` 必须覆盖全部文件，CI 双向比对。

## 后果

- **正面**：决策轨迹可追溯；推翻决策有据可依；过时设计稿可以整体移出仓库而不丢理由。
- **负面 / 成本**：每篇 40–60 行，写一条 ADR 约 0.5 小时；ADR 与代码可能脱节（缓解：ADR 里「如何验证仍被遵守」必须指名测试或 CI 规则）。
- **中性**：评审时多一步「这次改动是否需要 ADR」，判据见 `documentation.md` 4.3。
- **如何验证仍被遵守**：CI 的索引一致性检查（文件 ↔ `decisions/README.md` 双向比对）+ 评审模板中的 ADR 勾选项。

## 备选方案

| 方案 | 未采纳原因 |
| --- | --- |
| 把决策写进设计文档的「历史」小节 | 文档会无限增长，且读者无法区分哪些结论仍有效 |
| 只靠提交信息 | 提交粒度是一次改动，不是一次决策；跨提交的决策找不到入口 |
| 用 Issue 承载决策 | Issue 会关闭、会迁移，且与代码不在同一仓库版本中 |
